## A. КРИТИЧЕСКИЕ ИСПРАВЛЕНИЯ

### A-1. Секреты уезжают в APK: `.env` включён в assets
`pubspec.yaml` (`flutter: assets:`) содержит строку `- .env`, а сам `.env` (в нём `DEEPSEEK_API_KEY` для OpenRouter, `GEOAPIFY_API_KEY`, `WEATHER_API_KEY`) лежит в корне проекта. Любой, кто скачает APK, распакует его и прочитает `.env` как обычный ресурс — получит все три ключа. `README.md` при этом утверждает обратное («Файл `.env` **не включается** в assets приложения»), т.е. документация вводит в заблуждение.

`--dart-define` тоже не решение: ключ всё равно попадает в бинарник (строковая константа) и достаётся из `libapp.so`/`resources.arsc`.

**Что делать:**
1. Убрать `.env` из `assets` в `pubspec.yaml` (оставить только `.env.example`).
2. **Считать ключи скомпрометированными и ротировать** `DEEPSEEK_API_KEY`/OpenRouter, `GEOAPIFY_API_KEY`, `WEATHER_API_KEY`; проверить расходы в OpenRouter/WeatherAPI/Geoapify за прошлые периоды.
3. Вызовы AI вынести на сервер: Cloud Function или ваш VPS как прокси (`POST /advice`), ключ только на сервере, плюс лимит на пользователя, App Check-токен и валидация входа. Клиент обращается к своему прокси без ключа.
4. Отозвать/ограничить ключ Geoapify по bundle/appId; для WeatherAPI — по домену/IP.

### A-2. Firestore security rules отсутствуют как файл; клиент пишет в базу напрямую
`firestore.rules` содержит **не правила, а JSON индексов**: `{"indexes": [], "fieldOverrides": []}` (файл определяется как `JSON text data`). `firebase.json` ссылается и на `rules: firestore.rules`, и на `indexes: firestore.indexes.json` — последнего файла в репозитории **нет вообще**, т.е. `firebase deploy` для Firestore гарантированно падает, а правила в репозитории никогда не были настоящими.

Каталога `functions/` нет — Cloud Functions не используются, при этом все записи идут прямо с клиента:
- `lib/registration_page.dart:325` — создание `users/{uid}`;
- `lib/utils/database_helper.dart:690,701` — `users/{uid}/cars/{id}` (`set`/`delete`);
- `lib/utils/history_manager.dart:281-286,300-305` — `users/{uid}/history/{id}` (`set`/`delete`).

**Что делать:**
1. Написать настоящие правила: доступ только владельцу (`request.auth.uid == uid`), `deny` по умолчанию, валидация схемы полей и типов, запрет `list` на коллекцию без ограничения (иначе перечисление), `write: false` для всего, что должно писаться сервером.
2. **Проверить в консоли Firebase, что задеплоено сейчас.** Если проект создавался в тестовом режиме и правила не менялись — база открыта на чтение/запись всему интернету; это уже утечка (email, города, история заправок и авто всех пользователей).
3. Разделить на `firestore.rules` (правила) и `firestore.indexes.json` (индексы), починить `firebase.json`.

### A-3. Пароли подписи закоммичены в git
`android/keystore.properties` **отслеживается git** (`git ls-files` → `android/keystore.properties`) и содержит `storePassword`, `keyPassword`, `keyAlias`, `storeFile`. Правило `.gitignore` для него написано, но на уже отслеживаемые файлы не действует.

**Что делать:**
1. `git rm --cached android/keystore.properties` + коммит; хранить как `android/keystore.properties.example`.
2. Ротировать пароль keystore (и/или создать новый keystore) — старые значения считать утёкшими.
3. Если репозиторий публичный — вычистить файл из истории (`git filter-repo`) и **немедленно** сменить пароли; при уже опубликованном APK: зарегистрировать новый upload key в Play Console (Play App Signing позволяет сменить upload key).

### A-4. Миграция БД ломает обновление приложения (потеря доступа к данным)
`lib/utils/database_helper.dart:177` и `:186` — два раза подряд одна и та же команда:
```dart
if (oldVersion < 7) { ALTER TABLE fuel_logs ADD COLUMN weather_multiplier REAL }
if (oldVersion < 8) { ALTER TABLE fuel_logs ADD COLUMN weather_multiplier REAL }   // duplicate column
```
При обновлении с версии БД ≤ 6 сначала колонка добавляется, потом та же команда падает с `duplicate column name: weather_multiplier`, `catch` делает `rethrow`, `openDatabase` завершается ошибкой — **приложение перестаёт открываться у всех старых пользователей**. Сейчас БД v12, т.е. это срабатывает у каждого, кто пропустил несколько релизов.

**Что делать:** удалить дубль (v8 должен быть no-op или `DROP`/реальная новая миграция); каждую миграцию обернуть в собственный `try/catch` с логированием и без `rethrow` для идемпотентных ALTER (использовать проверку `PRAGMA table_info`); написать тест миграции (см. C-6) и проверить апгрейд 1→12 на копии реальной БД.

### A-5. Тесты не проверяют ничего критичного (ложно-зелёные)
`test/database_helper_test.dart:14`: `if (identical(1, 1.0)) { sqfliteFfiInit(); ... }` — условие **всегда false**, инициализация FFI никогда не выполняется. Все 4 теста работают на `MockDatabase` с матчерами `any` и заранее заданным ответом `query`. Проверяется только «метод вызвал mock». Нет ни одного теста на: миграции БД (A-4), двустороннюю синхронизацию (B-1), premium/IAP (A-7), дедупликацию истории, расчёт коэффициентов.

**Что делать:** заменить моки на реальный `sqflite_common_ffi` в памяти (`inMemoryDatabasePath`), добавить тесты миграций всех версий и сценариев синка; убрать фиктивное условие.

### A-6. App Check включается только на экране регистрации
`lib/registration_page.dart:53,76-85` — `FirebaseAppCheck.instance.activate(...)` вызывается из `initState` страницы регистрации. Возвращающийся пользователь (флаг `is_registered` уже стоит) этот экран никогда не открывает → App Check не активирован, его токена нет. Отсюда две ветки: либо в консоли enforcement **выключен** (и тогда App Check не защищает вообще ничего, а Firestore-правила должны быть в любом случае); либо enforcement включён, и приложение сломано у всех, кроме новых регистраций.

**Что делать:** перенести активацию в `main()` сразу после `Firebase.initializeApp`, добавить `debug`-провайдер для debug-сборок (`kDebugMode` → `AndroidProvider.debug` + зарегистрированный debug-токен), и только затем включать enforcement в консоли.

### A-7. Premium — флаг в SharedPreferences, а не покупка; productId расходятся
- Единый источник «премиума» для синхронизации — `SharedPreferences` (`providers/app_settings_provider.dart:64-69`, `utils/history_manager.dart:29-31`, `utils/database_helper.dart:596-600`). Значение можно выставить вручную (root/бэкап приложения) — вся платная синхронизация открывается бесплатно.
- **Разные productId:** `fuel_calculator_page.dart:202` ждёт `'supergrok_monthly'` (похоже на копипаст из чужого проекта), `settings_page.dart:33` покупает `'fuelmaster_premium_subscription'`. Итог: после покупки в «Настройках» экран калькулятора премиум не видит; продукт `'supergrok_monthly'` в Play вообще не существует.
- `settings_page.dart:57` регистрирует новый `purchaseStream.listen` **при каждом нажатии «Купить»** — утечка листенеров.
- Верификации чека нет (ни Play Developer API, ни сервера), нет обработки `PurchaseStatus.error`/`canceled`/`pending`, нет `restorePurchases` при старте приложения (только на экране калькулятора), нет учёта подписки после переустановки.
- `history_page.dart:81` читает свой `_isPremium` из prefs отдельно от провайдера — третья копия правды.

**Что делать:** один сервис `PremiumService` (единственный источник), серверная запись entitlement (`users/{uid}/entitlements`) + валидация чека на сервере, единый productId, один подписчик `purchaseStream` на всё приложение, `restorePurchases` в `main()`, корректная обработка всех `PurchaseStatus`.

### A-8. Release-блокеры идентификаторов и версий
`android/app/build.gradle.kts`: `namespace`/`applicationId = "com.example.fuelmaster"`, `versionCode = 1`, `versionName = "1.0.0"`, при этом `pubspec.yaml` — `version: 1.0.1+7`. Идентификатор `com.example.*` **нельзя будет изменить после публикации в Play**, и Play может отклонить приложение с таким applicationId. Версии в двух местах расходятся → непонятно, что реально собрано.

**Что делать:** до любой публикации сменить applicationId на реальный (например `ru.yugov.fuelmaster`), синхронизировать versionCode/versionName с pubspec, держать одно место правды.

## B. РЕКОМЕНДУЕМЫЕ ИСПРАВЛЕНИЯ

### B-1. Двусторонняя синхронизация может удалить данные пользователя
- `database_helper.dart:645-650`: локальные авто, которых нет в Firestore, **удаляются из локальной БД**. Сбой сети/частичное чтение = удаление машин и (через `deleteCar`) связанных записей истории.
- `database_helper.dart:478-484`: `getUserCars()` дедуплицирует по номеру, при этом ключ для машин **без номера — пустая строка** (`car.licensePlate ?? ''`), т.е. все авто без номера схлопываются в одну запись и участвуют в синке как «лишние».
- Сопоставление записей идёт по локальному `AUTOINCREMENT id` (`:615-624`, `history_manager.dart:247-250`) — на втором устройстве id другие, поэтому один и тот же автомобиль считается разными, конфликты решаются по `last_modified`, а расхождение id ломает `firstWhere`.
- `history_manager.dart:266` вставляет удалённые записи без проверки и без tombstone — «удалил на телефоне → вернулось с облака».

**Что делать:** UUID для авто и записей (не автоинкремент), мягкое удаление с tombstone-полем и `deleted_at`, синк «только вверх» без удаления локального, явная стратегия разрешения конфликтов (last-write-wins по серверному времени + журнал изменений), не удалять ничего автоматически в первом релизе исправления.

### B-2. Синхронизация запускается на каждое действие
`providers/car_provider.dart:29-35`: `loadCars()` после `addCar`/`updateCar`/`deleteCar` выполняет полный сетевой проход `syncCarsWithFirestore`. Плюс `history_page.dart:117-127` делает `syncHistoryWithFirestore` + ещё один `loadHistoryFromDatabase` при каждом открытии. Это лишние запросы, расход батареи и квоты Firestore.
**Что делать:** убрать синк из `loadCars`; синхронизировать по явному событию (вход в аккаунт, pull-to-refresh, периодически/по изменению), с дебаунсом.

### B-3. Дублирующиеся вызовы AI и логирование ответов
`fuel_calculator_page.dart:243-248`: при пустом ответе сервис вызывается повторно, а внутри `deepseek_service.dart` уже есть `maxRetries = 2` → до 3 платных запросов на одно нажатие. `deepseek_service.dart:79` пишет в лог **всё тело ответа**, `:81` — весь текст совета.
**Что делать:** один вызов на действие, ретраи только на сетевых ошибках/429/5xx с экспоненциальной паузой; логировать статус, код и длину, но не тело.

### B-4. HTTP-запросы без таймаута
`deepseek_service.dart:61`, `registration_page.dart:175,257`, `weather_service.dart:17` — нет `.timeout(...)` и нет обработки `TimeoutException`. При «залипшем» соединении пользователь видит вечный спиннер (`_isLoading` в калькуляторе не сбрасывается).
**Что делать:** `.timeout(const Duration(seconds: 10))` + отдельная обработка таймаута с понятным сообщением; общий `http.Client` с настройками.

### B-5. Опасные касты чисел
`weather_service.dart:79-81` — `weatherData['current']['temp_c'] as double`: WeatherAPI возвращает целые числа как `int` (например `20`), каст бросает `TypeError`; то же для `precip_mm`, `wind_kph` и для `multiplier as double` (`:94,108,123`). Метод вызывается из расчёта топлива — при определённой погоде расчёт падает.
**Что делать:** `(v as num).toDouble()` везде, где приходит JSON/SQLite-значение; закрыть тестом с int-значениями.

### B-6. Геолокация на старте приложения
`app_initializer.dart:26-40` вызывает `LocationService().getCurrentCity()`, который **сразу запрашивает разрешение** (`location_service.dart:11`) — до онбординга и без объяснения (Play-политика: разрешение запрашивается в контексте), а `Geolocator.getCurrentPosition` без `settings`/таймаута может ждать долго. Дальше `splash_screen.dart:38` добавляет ещё фиксированные 2 секунды. На первом запуске пользователь «висит» на сплэше и получает запрос разрешения «из ниоткуда».
**Что делать:** не трогать геолокацию до онбординга; запрашивать разрешение на экране города (он уже есть в регистрации), с таймаутом и фолбэком на «Москва/New York»; убрать фиксированную задержку сплэша, ждать реальную инициализацию.

### B-7. Экспорт/шэринг файлов
- `history_page.dart:219-124` (блок `try/finally`): временный файл **удаляется сразу** после `Share.shareXFiles`, хотя получающее приложение ещё может его читать → битый файл/ошибка у получателя.
- `fuel_calculator_page.dart:361-376` формирует CSV в `getApplicationDocumentsDirectory()` и просто показывает снекбар — файл пользователю недоступен (Android 11+).

**Что делать:** удалять временный файл при следующем старте (или не удалять), CSV формировать и сразу отдавать через `SharePlus.instance.share`, добавить колонки авто/номера/условий (сейчас названия «съедаются» `split(': ').last`, что ломает значения с двоеточиями).

### B-8. Рассинхрон состояния в UI
- `main.dart:79-97`: `_pages` собирается один раз в `postFrameCallback` и больше не пересобирается → после смены языка/темы страницы сохраняют старые `locale`/`isDarkMode`; списки передаются по ссылке (`historyProvider.history`).
- `history_page.dart:57,81` хранит собственную копию истории и собственный `_isPremium`.
- `main.dart:100-105`: `Provider.of(context)` вызывается в `dispose()` → исключение «looked up a deactivated widget's ancestor»; там же `AdManager.dispose()`, а он же вызывается в `history_page.dart:105` — SDK рекламы гасится при уходе с экрана истории и больше не оживает (реклама пропадает до перезапуска).
- `_loadHistory()` в `history_page` мутирует `widget.history` (`clear/addAll`) — небезопасно и завязано на внешний список.

**Что делать:** строить страницы в `build`/через роутер, читать состояние только из провайдеров (`context.watch`), вынести рекламу в один владелец жизненного цикла (не в `dispose` страницы), не вызывать `Provider.of` в `dispose`.

### B-9. Межстраничная реклама никогда не показывается
`fuel_calculator_page.dart:697` вызывает `AdManager.showInterstitialAd()`, но `AdManager.loadInterstitialAd(...)` **не вызывается нигде** в коде → на нативную сторону приходит «показать то, чего нет». Там же `adUnitId` захардкожены (`"R-M-16174255-1"`, `"R-M-16174255-2"`), хотя в `.env` есть `YANDEX_*_AD_UNIT_ID` — дублирование источника правды.
**Что делать:** грузить межстраничную рекламу заранее (после показа расчёта, с частотным ограничением), показывать только при `isLoaded`, ID брать из одного места.

### B-10. Частичная регистрация
`registration_page.dart:317-330`: пользователь создаётся в Firebase Auth, затем идёт запись профиля в Firestore. Если запись падает (нет сети/правила), показывается ошибка, но аккаунт в Auth уже создан → повторная регистрация даёт «email already in use», а в базе нет профиля.
**Что делать:** сначала `createUserWithEmailAndPassword`, затем запись профиля с ретраями; при провале — перевести пользователя в режим входа с сообщением «аккаунт создан, войдите»; профиль создавать также при входе (`ensureUserProfile`).

### B-11. Состояние «зарегистрирован» живёт в prefs, а не в Auth
`main.dart:198-201` смотрит только `appSettings.isRegistered`; `FirebaseAuth.authStateChanges()` не слушается (нет ни `StreamBuilder`, ни подписки). Итоги: выход из аккаунта на другом устройстве/отзыв токена не отражается; `signOut` (`settings_page.dart:88-93`) чистит премиум?—нет, но оставляет локальные данные (`Settings` не удаляет SQLite) → следующий аккаунт на том же устройстве видит чужие авто и историю.

### B-12. Приватность/политики
