# Где хранить базу автомобилей: онлайн, офлайн и защита от копирования

Дата: 13.09.2026. Проект: FuelMaster (Flutter + Firebase, `fuelmaster-984fb`).

Требования, которые надо выполнить одновременно:

1. **Офлайн** — приложение работает без интернета (у пользователя в дороге сеть есть не всегда).
2. **Онлайн-обновления** — новые модели появляются без выпуска новой версии в Play.
3. **Защита** — накопленную базу не должно быть просто «унести».

---

## 1. Честная граница: что защищаемо, а что нет

| Что | Защитимо? | Почему |
|---|---|---|
| Данные МИИТ КНР (нормы расхода) | **Нет и не нужно** | Открытые государственные данные. Их может взять любой — как и мы |
| Наша обработка: сопоставление CN↔рыночных названий, дедупликация, исправления | **Частично** | Внутри APK — извлекаемо. Защищено только на сервере |
| Реальные расходы пользователей (агрегат по заправкам) | **Да** | Никогда не покидает сервер; в клиент попадает только обезличенный агрегат |
| Целостность доставки (никто не подменил данные) | **Да, полностью** | Электронная подпись + хеш |

**Ключевой вывод.** Любые данные, вшитые в APK, извлекаются — распаковкой или чтением локальной SQLite после установки. Значит защита строится не на «спрятать», а на **разделении слоёв**: в приложение попадает только нужное для офлайна, всё остальное отдаётся сервером по запросу.

## 2. Целевая схема — три слоя

```
┌─ Слой 1. ВСТРОЕННЫЙ СНИМОК (офлайн гарантирован) ──────────────┐
│ assets/cars.csv  →  SQLite на устройстве                        │
│ Market-подборка: массовые модели RU/KZ + все классы             │
│ Обновляется только с новой версией приложения                   │
└────────────────────────────────────────────────────────────────┘
              ▲ при первом запуске проверяется manifest (слой 2)
┌─ Слой 2. ПОДПИСАННЫЕ ОБНОВЛЕНИЯ (онлайн, без релиза) ──────────┐
│ manifest.json (версия, url, sha256, подпись Ed25519)            │
│ delta-обновление: добавленные/исправленные строки               │
│ Применяется транзакцией; при ошибке — откат к слою 1            │
└────────────────────────────────────────────────────────────────┘
┌─ Слой 3. СЕРВЕР (полный каталог, то, что реально ценно) ───────┐
│ Полный каталог 138 350 записей + сопоставления названий         │
│ Агрегаты реального расхода по факту заправок                    │
│ Доступ по API-ключу + Play Integrity, лимит запросов            │
└────────────────────────────────────────────────────────────────┘
```

Приложение всегда стартует со слоя 1 — сеть не нужна вообще. Слой 2 только улучшает каталог. Слой 3 нужен для редких, «глубоких» запросов (полный каталог целиком вшивать нельзя: 138 350 строк — это ~25–30 МБ в ассете и заметное время первичного импорта на телефоне).

## 3. Где конкретно хранить

| Слой | Где | Почему так |
|---|---|---|
| 1. Снимок | Git-репозиторий → `assets/cars.csv` | История изменений, откат, воспроизводимость сборки |
| 2. Манифест + дельты | Существующий VPS (`maksim.yugov.89.hlab.kz`) + nginx, файлами | Уже есть, не нужно платить за egress; статика отдаётся быстро и дёшево |
| 3. Полный каталог + агрегаты | VPS2 (Нидерланды) или тот же VPS, PostgreSQL | Только по API, с авторизацией и логами |
| Резервные копии | GitHub Release (приватный) + локальный `C:\Users\Despa\fuelmaster-backups` + сервер | Правило 3-2-1: три копии, два носителя, одна вне офиса |

**Почему не Firebase Storage / Firestore для базы.** Оплата за скачивание: полный каталог на 138 тыс. записей при тысяче пользователей — это десятки гигабайт трафика в месяц, а обновления каталога тянут все клиенты. Статистическая раздача файлов с собственного VPS обходится фиксированной ценой. Firebase остаётся для того, для чего он хорош: Auth, Remote Config, аналитика.

**Remote Config для указателя.** В Remote Config лежит только маленькая запись: версия каталога, URL манифеста, sha256. Логика изменения каталога отделена от релиза приложения.

## 4. Защита по шагам

1. **Подпись всего, что приходит из сети.** Ed25519: приватный ключ — только на машине сборки и на сервере, публичный вшит в приложение. Клиент проверяет `sha256` файла и подпись манифеста и **не применяет** данные, если подпись не сходится. Это защищает не «от копирования», а от подмены — то есть от главного риска: чтобы через наш канал пользователю не приехала чужая база или испорченные нормы.
2. **Не вшивать полный каталог.** В APK — только массовая подборка. Полный каталог и сопоставления — на сервере.
3. **Доступ к API ограничен.** Firebase App Check + Play Integrity: запросы принимаются только от настоящего приложения с настоящего устройства. Плюс лимит: например, не более N запросов в минуту на устройство. Это не остановит целенаправленного копировальщика, но делает сплошную выкачку дорогой и заметной.
4. **Логирование аномалий.** Всплеск скачивания полного каталога с одного устройства — сигнал. Достаточно писать в лог и уметь закрыть доступ.
5. **Юридический слой.** Экран «Источники данных» со ссылкой на первоисточник, версия каталога и дата, пункт в условиях использования о запрете извлечения базы целиком. По праву РФ/РЗ составная база данных охраняется как объект смежных прав изготовителя — это даёт основание для претензии, если базу скопировали целиком и выложили.
6. **Маркировка-ловушка (по желанию).** Пара служебных записей с уникальными написаниями, которых не бывает в реальном реестре. Если они всплывут в чужом приложении — это прямое доказательство источника утечки. В пользовательский интерфейс такие записи не выводятся.

**Чего сделать нельзя, чтобы не обманывать себя:** нельзя защитить вшитый CSV от копирования, нельзя «зашифровать» его так, чтобы работало офлайн и при этом не расшифровывалось на устройстве: ключ всё равно лежит в APK. Всё, что продаётся как «защита офлайн-базы», сводится к усложнению.

## 5. Порядок внедрения

| Фаза | Что делается | Зависимости |
|---|---|---|
| 1 | Сбор и импорт каталога МИИТ, формирование `assets/cars.csv` | Сделано (см. `CAR_DB_EXPANSION_2026-09-13.md`) |
| 2 | `tools/build_catalog.py`: сборка снимка + `manifest.json` с sha256 и версией. Локально, без сервера | Ничего |
| 3 | Проверка версии каталога при старте: если в манифесте версия выше — предложить обновление; проверка подписи и хеша; применение транзакцией с откатом | Публичный ключ Ed25519 |
| 4 | Публикация манифеста и дельты на VPS, подключение Remote Config | Доступ к VPS |
| 5 | Полный каталог через API с App Check и лимитами | Аккаунт Firebase Blaze (уже есть) |
| 6 | Агрегат реального расхода по заправкам (k-анонимность: не менее 5 пользователей на модель) | Накопленные данные |

Фазы 2–3 не требуют сервера вообще и могут быть сделаны сразу: они дают обновляемый каталог и проверку целостности уже сейчас.

## 6. Ограничения

* Схема не мешает конкуренту легально собрать те же данные МИИТ самостоятельно: они открыты. Защищается не истина, а работа — сопоставление названий, проверка, агрегаты реального расхода.
* Первичный импорт каталога на устройстве должен оставаться быстрым: при росте снимка свыше ~50 тыс. строк нужен предварительно собранный SQLite-файл вместо CSV (импорт через `batch` остаётся, но из файла базы — на порядок быстрее).
* Приложение должно работать и при полностью недоступном сервере: любая ошибка сети — не блокирующая, каталог берётся из снимка.
